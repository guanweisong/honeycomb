# 类型安全治理

规范验收以 [type-safety-governance](../../../openspec/specs/type-safety-governance/spec.md) 为权威；以下内容指导查找、迁移和验证，不另定义业务写入或恢复协议。涉及具体业务协议时按[架构规则索引](../frontend-structure/references/architecture.md)定位。

## 核心原则

生成或修改类型敏感代码时，先按本 Skill 设计真实契约，审计清理只是补救。目标是消除不真实的类型承诺，而不是追求字符层面的“零断言”。先修正信息来源，再窄化；只有公开类型确实无法表达时，才保留最小且有说明的适配断言。

## 生成前：唯一事实源

此规则适用于日常新增代码，不以用户要求审计或清理为前提。同一语义只维护一个权威定义，其他位置引用、推导或显式转换。

在新增类型、schema、常量或转换函数前，先用 `rg` 搜索概念名、关键字段和现有消费者，确定「概念 → 所属模块的权威定义 → 本次复用方式」。找到了相同语义的定义就直接复用，不先复制再计划清理。仅遇到归属或语义冲突时向用户解释选择，不要求每次输出冗长清单。

| 情况                                                           | 生成方式                                                                                                                 |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 已有权威类型，当前不需要运行时校验                             | 引用该类型；同语义子集用 Pick/Omit，不能重写字段集合                                                                     |
| 同一 DTO 同时需要静态类型和表单/API/JSON/cache 校验            | 在所属模块建立唯一运行时 schema，由 z.input/z.output/z.infer 推导类型；命令、解码器和消费者引用它，不手写第二套结构      |
| schema 已存在但需要不同错误文案                                | 复用权威 schema 或工厂，仅定制文案，不复制校验规则                                                                       |
| Feature 纯契约或公开出口                                       | 直接复用权威模型，不再通过 ReturnType 等重建同名模型或新增集中转发层                                                     |
| 新增跨模块消费者                                               | 通过所属 feature 的纯 schema/type/catalog 或有意复用的具名入口引用；不建立转发层，不把 ORM 或服务端运行时带入纯契约或 UI |
| 已有枚举成员、事件、提供商、缓存 namespace、语言或 UI 字段目录 | 从权威目录派生类型、白名单和标签；模块专属常量留在所属模块                                                               |

领域枚举或数值范围同时属于持久化不变量时，Drizzle CHECK、Feature Zod schema 与服务端持久化读取窄化必须从同一权威目录派生。新增或收紧 CHECK 前先提供只读数据审计，只报告表、字段和数量；发现不兼容数据必须中止迁移，不得自动选择、删除或回显原始值。SQL、Journal、Snapshot 必须一一对应，并通过独占临时数据库重放验证结构。

权威位置由语义和依赖方向决定，不由最早出现的文件决定：Feature 的业务输入及命令校验可由该 Feature 的纯 Zod schema 所有，router/form 直接引用或按不同语义组合；仅服务于界面交互的 schema 留在所属 UI 边界。Drizzle 表定义归 lib/db/schema，ORM 运行时与查询对象仅用于服务端持久化实现；经过审计的读取字段投影类型例外严格按 [model-boundary-governance](../../../openspec/specs/model-boundary-governance/spec.md) 的精确路径和 type-only 白名单执行，不能扩大为 types/ 或 DB 目录许可；feature server 函数可以直接访问数据库。Feature 纯业务 schema 不得导入 UI、router、ORM 或数据库实现。

新增写入或缓存契约时，不能以「编译通过」「有返回类型注解」「satisfies/extends 检查通过」为由，保留业务 interface 并另写一份覆盖同一模型的 Zod object。兼容性检查只能发现部分漂移，不能让两个字段清单成为唯一事实源。保留原调用签名可以通过类型别名迁移实现，不要求复制定义。若用户明确禁止修改权威来源所需文件，先说明冲突和最小必要调整，不静默新增重复契约。

派生前用旧契约验证可选语义：Zod optional 的 `undefined` 与手写可选属性在 `exactOptionalPropertyTypes=true` 下不一定相同；同时检查开关两种模式的目标契约，不因此宣称整个应用已经支持该严格选项。SDK 的泛型方法 `ReturnType` 可能退化为 `any`，应实例化真实调用选项或使用公开权威响应类型，并增加字段精度负例。枚举字符串兼容、输入/输出与 repository/API 默认策略分别保留；不为派生添加通用泛型或新的运行时 schema。

不同语义不能为去重强行合并：公开/后台响应、完整/部分语言、输入/持久化值、身份用户/关联快照分别明确命名及转换。类型注解或 Omit 不会在运行时删掉敏感字段，公开响应必须实际选择允许公开的字段。仅字段偶然相同、规则和生命周期不同，不提取万能 DTO 或泛型 CRUD 层。

迁入 types/ 时不要把整个目录当作纯类型或整目录放行：派生 DTO 文件仅保留 type-only 依赖，每个 enum 独立文件；schema 只值依赖中立 enum/catalog，不依赖由 schema 推导的 DTO 或展示枚举。具体目录约束以权威规范为准。

迁移时按数据流搜索消费者，至少检查读取、写入、通知/后台任务、缓存、transport、presentation 及测试；不能只按原类型名或最显眼的两个调用点搜索。更新所有消费者后删除无用途的副本与旧出口。测试预期应独立书写，不从权威实现重新计算；以架构门禁检查出口归属，以 schema 组合、边界行为和序列化往返测试检查字段保留，不能用「两份结构暂时相等」的测试维持双重维护。

统一共享配置前先记录各边界现有行为。相同字面量不必然是相同策略：API、数据库读取、UI 的默认分页或排序，路由语言顺序、公开/后台白名单可能有独立语义。相同策略从一个目录派生；不同策略分别具名并复用共同基础，不能为去重直接统一数值、顺序或回退行为。已有缺陷不因去重自动获得行为修改授权。

## 断言与窄化处理顺序

对每个 `any`、`as`、`!` 或规则抑制依次判断：

1. 修正源类型或跨层 DTO；
2. 使用控制流、类型谓词或判别联合窄化；
3. 缺失值合法时使用 fallback 或提前返回；
4. 缺失值违反不变量时增加已测试的错误分支；
5. 第三方公开类型无法表达时，在适配边界保留最窄断言并写明原因。

新增运行时分支时，**REQUIRED SUB-SKILL:** Use superpowers:test-driven-development。

## 适用边界

涉及 feature 归属、服务端操作或 ORM 隔离时，**REQUIRED SUB-SKILL:** Use feature-architecture。本 Skill 不重复定义目录架构，只补充类型逃逸的处理方式。

| 场景                | 要求                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| 跨边界契约          | 修正源 DTO；不得用 `any`、`as` 或开放式记录掩盖层间类型泄漏                                    |
| server 函数测试依赖 | 使用真实数据库/技术接口的 typed mock、fixture 或实际所需的最小子集，不为测试制造 Repository 层 |
| App Router 参数     | 保持外部参数为 `string`，经运行时校验或规范化后再作为领域联合类型使用                          |
| 可空展示数据        | 日期、媒体尺寸、关联记录等必须显式处理缺失值，不使用非空断言掩盖                               |
| 测试 fake           | 使用 `Pick`、准确 fixture、typed factory 或 `satisfies`；禁止用 `as never` 伪装完整业务契约    |
| 第三方测试替身      | 通过单一辅助函数建立 `unknown` 边界，调用点不重复强转                                          |

## 可以保留的类型表达

- `as const` 字面量与只读窄化；
- 经过运行时校验后，在品牌类型构造器内部建立品牌的断言；
- Drizzle、Better Auth、Zod resolver、React 或其他第三方未公开内部类型所需的局部 `unknown` 适配；
- 框架泛型 API 返回 `unknown` 且调用点掌握列定义等可靠上下文时的最小断言。

第三方边界必须同时满足：位于具名 adapter 或测试 helper、返回固定目标类型、输入输出结构最小、调用路径受限。不得接受由调用方任意指定的目标泛型，也不得承载业务 DTO 转换。

若测试 helper 必须返回 `Database` 等完整框架类型，只能用于该框架的低层 adapter、context 或集成测试；纯业务 fixture 必须使用实际所需的最小结构；直接数据库操作的测试可使用真实数据库接口的集中 typed mock，不把强转分散到业务调用点。

这些边界不得改写为通用 `cast<T>()`、`asMock<T>()` 或扩散到业务调用点。非显然双重断言必须在相邻注释中说明具体类型缺口和可移除条件；治理门禁应对允许位置使用窄路径清单。

## 治理门禁

静态门禁只禁止高风险模式：生产代码的显式 `any`、`as never`、`no-explicit-any`，以及无边界说明的双重断言。不得用全局正则禁止所有 `as`、`!` 或单词 `any`，以免误报 `as const`、`expect.any`、导入别名、CSS 和英文文本。指定文件或指定名称的 AST 门禁只证明其覆盖范围；新增权威契约时，同时加入真实消费者行为测试，并复扫同模块及跨层消费者。

验证应与改动风险成比例，并遵循受影响工程 Skill 的质量门禁：

- 修改类型或运行时代码时运行 `bun run check-types`、`bun run lint`、相关测试和 `git diff --check`；仅文档/Skill 同步按质量门禁选择规格、链接与文档检查；用户限定或环境阻塞的未运行项明确披露；
- 跨边界契约、共享测试基础设施或大范围治理变更运行完整单元测试与覆盖率；
- 仅在变更影响生产构建、框架边界，或对应质量门禁要求时运行 `bun run build`。

交付唯一事实源审计时明确列出：已收敛的权威定义、刻意保留的不同语义、扫描和测试覆盖范围，以及尚未验证的边界。类型、Lint 或局部门禁通过不能表述为「全工程不存在任何重复」，除非已有相应的全工程证据；结构扫描也不能证明名称不同的业务规则语义等价。

若工作属于 OpenSpec 变更，**REQUIRED SUB-SKILL:** Use openspec-apply-change，并用中文同步对应工件。本 Skill 不重复定义 OpenSpec 流程。不得为了通过门禁修改公开输入协议、数据库 schema、迁移或依赖，除非用户明确扩大范围。

## 常见错误

- 把所有断言一律删除：会丢失合法 readonly、品牌和第三方边界语义。
- 用 `unknown` 原样替换 `any`：只是把契约问题推给消费者。
- 为每个操作新建单方法端口：优先测试直接 server 函数，只有真实外部适配需要时才保留最小技术接口。
- 用更隐蔽的辅助函数包装强转：类型逃逸仍然存在，只是更难审计。
- 先改实现再补空值测试：无法证明测试能捕获原问题。
- 用 `satisfies`、单向 `extends` 或相等性测试连接两份字段清单：仍需同时维护两个来源。
- 只迁移 query/command 而遗漏通知、后台任务或缓存消费者：重复映射会继续存在。
- 看到相同默认值就合并策略：可能无意改变入口的排序、分页、顺序或回退行为。
