## Context

五张内容主表及翻译表已经完成结构迁移，主要仓储也已从翻译行组装稳定的 `{ zh, en }` 读取模型。全面审计发现，评论后台的关联内容查询仍沿用主表含有 `title` 的旧假设；分类、页面和标签更新只执行 `UPDATE`，无法恢复意外缺失的必填 locale 行；此外还有少量重复类型与过时文档。

本次变更跨越评论、内容仓储、类型契约和文档，但不改变表结构与外部接口。

## Goals / Non-Goals

**Goals:**

- 评论后台以固定数量的批量查询加载关联文章、页面和自定义文章翻译，并组装现有标题模型。
- 分类、页面和标签更新按 locale upsert，保持事务原子性并恢复缺失行。
- 生产代码的多语言对象类型引用权威 `MultiLang`，清理旧字段模型残留。
- 用回归测试覆盖实际漏迁路径和缺失翻译行恢复。

**Non-Goals:**

- 不新增或修改数据库表、索引和版本化迁移。
- 不修改 tRPC、表单或公开读取模型的 `{ zh, en }` 形状。
- 不引入通用多态翻译仓储，不扩展支持语言集合。
- 不执行 E2E 或远程数据库写入。

## Decisions

### 评论关联翻译使用按实体类型批量加载

评论分页仍先查询 ID 和评论主记录，再分别按本页出现的 post/page ID 批量查询翻译表。所有文章型引用共用一次文章翻译查询，页面使用一次页面翻译查询，随后通过映射组装标题。

选择显式批量查询而不是逐评论关系查询，是为了保持查询次数与评论数量无关；选择复用现有 `assembleLocalizedField` 而不是新增评论专用多语言规则，是为了保持可空语义一致。

### 必填翻译用 SQLite 冲突更新

分类、页面和标签在更新包含该实体全部必填翻译字段时，对每个受支持 locale 执行 `INSERT ... ON CONFLICT(owner_id, locale) DO UPDATE`。这样既保持正常完整更新行为，也能在翻译行缺失时补回完整行；只修改部分必填字段时继续更新已有行，避免为缺失行臆造未提供内容。所有操作继续位于现有主记录更新事务中。

### 上层类型只引用权威定义

完整或可缺语言的文本统一引用 `MultiLang`；确实只消费局部字段的组件使用基于权威类型的 `Pick`/嵌套类型，而不重新声明语言键。历史迁移 SQL 中固定的 locale 和 JSON 解析不属于运行时重复事实源，继续保留。

## Risks / Trade-offs

- [评论列表增加翻译查询] → 查询次数为每页固定常数，并按去重 ID 批量执行，避免 N+1。
- [upsert 可能掩盖异常缺行] → 必填输入仍需同时提供两种语言，补回行为只恢复契约要求的数据，不制造翻译。
- [类型收敛可能暴露旧 mock] → 同步修正测试夹具，并通过完整类型检查和单元测试验证。
