## Context

项目已将认证、数据库、账号安全和领域模型分离。当前仍有两处跨层耦合：共享 UI 使用由完整 `AppRouter` 推导的用户输出类型；`trpc/api/utils/sendEmail.ts` 同时持有邮件基础设施、评论模板和设置输出类型。前者使 UI 依赖传输层，后者使基础设施反向依赖具体 tRPC feature。

## Goals / Non-Goals

**Goals:**

- 让共享 UI 仅依赖稳定、最小的用户展示契约。
- 让邮件发送和评论邮件模板独立于 tRPC 工具目录，并保持现有发送内容与失败日志。
- 区分 tRPC 输出类型与领域实体，统一局部目录命名。
- 用自动化测试约束新的依赖方向。

**Non-Goals:**

- 不把仍只被 tRPC 使用的限流、缓存、CAPTCHA 或 S3 适配器强行拆分为新包。
- 不改变数据库、认证会话、邮件提供商、公开 API 或页面行为。
- 不为单一用途逻辑创建泛化抽象。

## Decisions

### 共享用户展示契约放入 domain

在 `packages/domain/user` 导出仅包含 UI 所需字段的 `CurrentUser` 契约；tRPC 输出仍可在客户端通过 `AppRouter` 推导，但 UI 不再引用它。选择该方案而非在 UI 内声明类型，原因是用户身份展示由多个 UI 组件共享，且契约属于稳定业务概念。

### 通知能力按业务能力独立成包

创建 `packages/notifications`，其中包含 Resend 发送器、评论通知编排接口与邮件模板。评论 service 仍负责读取评论和站点设置，但将通知请求传给该能力。选择按能力分包而非保留在 `trpc/api/utils`，因为邮件服务和模板不属于 tRPC 传输层，并可能被其他入口复用。

### 保留 tRPC 专属基础设施

`rate-limit` 被 middleware 使用，缓存、CAPTCHA、S3 当前仅由 tRPC feature 使用；在出现第二个稳定消费者前保留其位置。这样避免只为目录对称性增加空包和迁移噪声。

### procedure 输出类型集中在传输层入口

将 procedure 输出推导类型集中在 `trpc/api/outputs.ts`，保留既有的消费者类型名称以避免无意义的调用方改名。它们不是领域实体，也不应散落在 feature 的 `types` 目录；服务端内部不依赖该入口。

## Risks / Trade-offs

- [移动邮件模块时导入路径或模板行为遗漏] → 为通知能力、评论 service 和包边界添加回归测试。
- [共享用户契约字段不足] → 先以现有 `AdminLayout` 与 `UserDropdown` 使用字段为准，避免暴露完整 tRPC 输出。
- [大范围文件重命名造成噪声] → 仅重命名明确遗留的 `libs` 和 `constans`，不做其他无语义价值的全仓重排。

## Migration Plan

1. 先建立失败的边界测试与通知模块测试。
2. 抽离共享用户契约、通知能力和输出类型文件，并更新消费者。
3. 迁移局部目录命名，删除空账户安全路由目录。
4. 运行单测、类型检查、Lint 和生产构建；任何失败均可通过回退本变更的文件移动恢复。
