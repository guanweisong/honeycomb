## Context

当前三个门禁分别存在“配置有声明、真实入口未执行”“命令成功、结果无法消费”“测试已存在、CI 未运行”的断层：Better Auth 配置了密码下限，但后台用户写入 Schema 和凭据落库服务没有复用该规则；`bun audit --json` 在 JSON 前输出 dotenv/版本信息，审计脚本直接解析完整 stdout；CI 只点名三个 E2E 文件，且主题与标签场景会因空数据库跳过。

这些问题跨越认证、供应链脚本和浏览器测试基础设施，但不要求修改生产数据库结构或公开 API。实现需要保持模块边界：身份包拥有凭据策略，用户应用层组合写入 Schema，脚本将不可信命令输出先解析再评估，测试数据只允许写入显式声明的本地 E2E 数据库。

## Goals / Non-Goals

**Goals:**

- 让后台账号创建、更新和底层凭据写入共同执行与 Better Auth 一致的 6–128 字符密码策略，并校验邮箱格式。
- 从带 ANSI、dotenv 提示和 Bun banner 的 stdout 中唯一提取审计 JSON；缺失或存在多个候选时失败关闭。
- 用可重复、幂等且限定本地数据库的种子数据支撑所有现有 Chromium E2E，CI 不再点名测试文件或条件跳过关键库存。
- 通过单元测试、契约测试和真实完整 E2E 证明三个门禁有效。

**Non-Goals:**

- 不改变登录标识、角色权限、密码哈希算法或现有数据库表结构。
- 不把 E2E 扩展到所有浏览器项目，也不引入外部托管测试数据库。
- 不改变依赖漏洞的生产依赖筛选规则或现有临时豁免政策。

## Decisions

### 1. 身份包拥有唯一凭据密码策略

在 `src/packages/identity/auth` 定义密码最小/最大长度和可复用 Zod Schema。Better Auth 配置、用户应用层写入 Schema及最终凭据写入函数都引用同一来源。邮箱规则由用户应用层写入 Schema负责，避免把用户资料契约反向放入身份基础设施。

仅在表单层校验会被直接 tRPC/API 调用绕过，仅在仓储层校验又无法为界面生成一致错误；因此在边界 Schema 与最终凭据写入处双重执行同一规则，形成纵深防御而不复制数值。

### 2. 使用结构感知扫描器解析 Bun 审计输出

解析器把 stdout 当作不可信文本，扫描字符串与转义状态，提取平衡的顶层 JSON 对象候选，再执行结构校验。ANSI 和普通前缀无需依赖固定 banner 文案。只有一个合法审计对象时继续；零个或多个合法对象都抛错。

按首个 `{` 到末个 `}` 截取虽然简单，但会在提示文本含花括号或串联多个对象时悄悄误判，不符合安全门禁的失败关闭要求。

### 3. CI 显式播种本地 E2E 数据库后运行完整 Chromium 项目

新增幂等种子脚本，为认证账号、设置、菜单、已发布文章、页面、分类和标签建立最小确定性数据集。脚本只接受本地 `file:` 数据库且要求显式 E2E 开关，拒绝远程 URL，降低误写生产数据风险。

质量工作流完成迁移与播种后执行 `playwright test --project=chromium`，不列举 spec 文件。依赖内容存在性的 `test.skip` 改为确定性断言；未来新增 spec 将自动进入门禁。

### 4. 以分层测试证明行为

密码和审计解析使用快速单元测试先红后绿；CI 命令、种子步骤和无条件跳过由仓库契约测试约束；最后在临时本地数据库上运行完整 Chromium 套件。这样既能精确定位回归，也能验证真实入口之间的组合行为。

## Risks / Trade-offs

- [密码最大长度可能拒绝历史上可提交的超长值] → 128 字符与认证入口保持一致，只约束新的创建和修改，不迁移现有哈希。
- [扫描器可能把提示中的 JSON 误认为结果] → 对候选执行审计对象结构校验，并要求唯一候选；歧义时失败而不是猜测。
- [完整 E2E 增加 CI 时间] → 仍只运行 Chromium 单项目，依靠已有并行能力，换取库存自动覆盖。
- [种子数据与页面查询契约漂移] → 种子使用正式 Drizzle schema 和稳定业务常量，完整 E2E 在同一门禁内立即暴露漂移。

## Migration Plan

1. 先合入共享策略、解析器和种子/工作流契约测试。
2. 在临时本地数据库执行迁移和种子，运行全部 Chromium E2E。
3. 无生产数据迁移；回滚时可恢复旧工作流和调用点，新增纯函数/测试数据不会影响生产库。

## Open Questions

无。实现边界和门禁范围已确认。
