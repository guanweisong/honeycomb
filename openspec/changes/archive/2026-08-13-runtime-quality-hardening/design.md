## 背景

工程采用 Next.js App Router、Better Auth、tRPC、Turso 与 Cloudflare。现有静态检查和单测基础良好，但覆盖率门禁、弃用的请求入口、生产限流降级、路由恢复体验和持续交付仍未形成可靠闭环。此次变更不调整领域模型和对外业务 API。

## 目标与非目标

**目标：**恢复覆盖率门禁；在生产启动时校验认证密钥；迁移至 `proxy.ts`；让生产 API 限流故障安全；提供路由恢复界面；以 CI 和依赖审计阻止质量回退。

**非目标：**不引入新的遥测供应商，不重写业务 UI，不在本次变更中替换数据库或认证框架。

## 决策

### 环境与认证

生产 `AUTH_SECRET` 使用最小长度和熵启发式校验；非生产保留可预测测试值以维持本地和 E2E 易用性。相比将校验完全交给 Better Auth 日志，此策略能在服务启动前失败并给出可操作错误。

### 请求入口与限流

将 `src/middleware.ts` 重命名为 `src/proxy.ts` 并导出 `proxy`，保持相同 matcher。限流器返回显式的“允许、拒绝、不可用”结果：生产缺失配置或 Upstash 故障时返回 503；开发与测试仅在 `NODE_ENV !== production` 时使用内存允许策略。相比静默放行，这优先保护公开接口；相比启动即失败，它避免暂态 Redis 故障使整站无法提供页面。

### 路由恢复

公共站点和后台分别放置 `loading.tsx`、`error.tsx`，并增加根 `global-error.tsx`。错误组件不显示异常详情，仅提供重试与返回入口。相比逐页面包裹 try/catch，可利用 App Router 的原生边界且不污染业务组件。

### 质量与供应链

补全环境解析的分支测试而不降低门槛。GitHub Actions 从锁文件安装，顺序执行类型、lint、覆盖率、构建、Cloudflare 验证和可离线运行的 E2E；依赖升级后以 `bun audit` 复核。相比只保留本地 Husky，此方案可在受保护分支强制执行。

## 风险与取舍

- [生产 Redis 未配置会导致 API 返回 503] → 在部署文档、启动验证和 CI 环境中提供明确配置路径；这是有意的安全性破坏性变更。
- [依赖升级存在 API 兼容问题] → 小步升级，每个直接依赖变更后运行类型、单测和构建。
- [错误边界可能掩盖诊断信息] → 继续通过 `instrumentation.onRequestError` 记录关联 ID 和安全错误上下文。
- [CI E2E 消耗时间] → 使用 Chromium 和现有测试环境变量，保留 trace 仅在重试时生成。

## 迁移与回滚

先发布包含 Upstash 生产配置和 `proxy.ts` 的版本；确认 CI、构建与线上 API 指标正常后再删除旧入口。若 Redis 服务不可用，可先恢复其服务；只有紧急情况下才回滚到上一部署版本。依赖升级由锁文件提交保证可重复回滚。

## 未决问题

无。生产环境必须配置 Upstash 是本次已确认的发布约束。
