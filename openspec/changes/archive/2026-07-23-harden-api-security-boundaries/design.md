## Context

项目使用 Next.js、tRPC 和 Drizzle ORM。文章、页面、分类、菜单和链接已经采用公开/后台双入口与轻量 service 模式，但用户、评论及部分公开辅助接口仍直接在 Router 中执行查询，导致资源可见性和响应字段安全规则分散。

本变更跨越多个 API 模块且涉及隐私字段、对象级授权和公共写操作，因此需要统一安全边界，但不需要引入完整 Repository 或 DDD 分层。

## Goals / Non-Goals

**Goals:**

- 在靠近数据库的位置强制资源发布状态和评论开关。
- 使用显式 DTO 阻止密码哈希及评论隐私字段进入公共响应。
- 验证评论目标唯一性和父子评论资源归属。
- 通过自动化测试覆盖每条新增安全规则。

**Non-Goals:**

- 不重构全部数据库访问。
- 不修改数据库结构。
- 不新增限流基础设施或浏览量去重策略。
- 不改变已封禁评论在前台以占位内容展示的现有产品行为。

## Decisions

### 采用轻量 Service/DAL

Router 负责输入、认证声明和错误映射；service 负责数据库查询、资源状态及关联关系校验。该结构与现有 `post.service.ts`、`page.service.ts` 和 `menu.service.ts` 一致。

替代方案是逐 Router 增加条件，改动更少但规则容易再次分叉；完整 Repository 重构则超出当前风险修复范围。

### 在数据库投影阶段生成安全 DTO

用户写操作使用显式 `.returning({...})`，评论公开响应通过公共 DTO 映射器生成。不会采用先查询完整记录再删除字段的方式，因为新增数据库字段可能被意外暴露。

邮件通知仍可使用服务端私有查询结果，但公开响应对象与通知对象相互独立。

### 评论验证集中为目标解析函数

目标解析函数接收 `postId`、`pageId`、`customId`，验证恰好存在一个标识。文章和自定义目标从文章表查询 `status` 与 `commentStatus`；页面从页面表查询 `status`，因为当前页面模型没有独立评论开关。

资源不存在或未发布统一表现为 `NOT_FOUND`，避免透露草稿存在；已发布文章关闭评论时表现为 `FORBIDDEN`。创建回复前额外读取父评论的三个目标字段并做完整元组比较。

### 公开辅助操作在 SQL 谓词中限制发布状态

浏览量更新和文章分类查询使用 `id AND status = PUBLISHED`，避免先读取再更新产生竞态，也避免调用者通过返回差异探测草稿详情。浏览量更新没有返回记录时抛出 `NOT_FOUND`。

## Risks / Trade-offs

- [评论目标校验增加数据库查询] → 只投影 `id`、`status` 和 `commentStatus`，以安全性优先。
- [评论关闭后前台列表不可见] → 这是统一“禁止读取或创建评论”的明确安全策略；恢复开关即可重新展示。
- [现有客户端依赖评论创建私有字段] → 当前前台只需要公共展示字段；通过类型检查确认无隐式依赖。
- [GUEST 失去用户列表访问] → 用户管理属于后台隐私能力，明确限制为 `ADMIN` 和 `EDITOR`。

## Migration Plan

1. 先增加失败测试，覆盖 DTO、权限、评论目标及发布状态。
2. 实现共享 DTO、标签 service 和评论目标验证。
3. 更新 Router 与后台标签调用点。
4. 运行类型检查、Lint、全量单测和生产构建。
5. 若发生回归，可整体回退本变更；无数据库迁移需要处理。

## Open Questions

无。评论限流和浏览量去重作为独立后续变更评估。
