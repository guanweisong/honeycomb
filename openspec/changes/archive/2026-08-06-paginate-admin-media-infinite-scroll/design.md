## Context

管理后台媒体页当前通过 `mediaQuery.ts` 使用 `limit: 99999` 请求全部媒体记录。`MediaGrid.tsx` 会为每条图片记录创建一个 Next.js `Image` 组件，导致媒体数量增长后首屏渲染和远程图片处理的资源消耗随数据量线性增长。

后端 `media.index` 已经支持 `page`、`limit` 和 `{ list, total }` 响应，不需要修改数据库或 API 契约。本次设计只调整客户端查询状态和列表加载时机。

## Goals / Non-Goals

**Goals:**

- 将单次媒体查询限制为固定页大小 50。
- 使用 `IntersectionObserver` 在接近列表底部时自动加载下一页。
- 在客户端按页追加结果，并阻止并发、越界和重置期间的重复请求。
- 保持已有上传、删除、选择和复制行为。
- 在浏览器不支持 `IntersectionObserver` 的环境中安全跳过观察逻辑。

**Non-Goals:**

- 不修改 `media.index` 后端接口、数据库表结构或排序规则。
- 不引入虚拟列表、第三方无限滚动库或新的运行时依赖。
- 不改变远程图片域名白名单和图片优化策略。

## Decisions

### 使用固定分页而非一次性加载

客户端每页请求 50 条记录，并在 hook 内维护已加载页。选择固定分页是因为后端已有分页能力，改动范围小且能直接限制单次响应和图片组件数量。相比继续使用超大 `limit`，分页能让内存占用随用户实际浏览范围增长。

### 使用 IntersectionObserver 而非 scroll 事件

在 `MediaPageShell.tsx` 底部放置哨兵元素，使用 `IntersectionObserver` 并设置 `rootMargin: "200px"` 提前加载下一页。相比 scroll 事件，这种方式不需要手动节流和计算滚动位置，也不会在每次滚动时执行回调。

### 在查询 hook 中维护分页状态

`mediaQuery.ts` 负责当前页、已加载页、总数、下一页加载和重置。页面容器只负责观察哨兵并调用 `loadMore`，网格组件继续只负责展示数据。这样分页协调逻辑不会泄漏到展示组件中。

### 使用请求页和结果签名防止重复追加

切换分页时数据层可能短暂保留上一页结果。hook 会记录请求页及上一页结果签名，只有结果真正变化后才写入新页缓存；同时使用请求状态和请求页引用阻止同一页被重复请求。

### 通过 reset 兼容上传和删除刷新

上传或删除成功后清空已加载页并回到第 1 页。hook 对外保留 `refetch` 名称作为兼容入口，但其行为改为执行完整分页 reset，避免在第 2 页直接 refetch 导致列表状态不一致。

## Risks / Trade-offs

- [风险] 用户快速滚动时可能连续触发多个分页请求 → 使用请求页引用、查询进行状态和总数边界共同阻止重复请求。
- [风险] 上传或删除后页面会重新加载第一页，用户当前滚动位置对应的后续页会消失 → 这是保证数据一致性的可接受代价，操作完成后从稳定的第一页重新开始。
- [风险] 没有 `IntersectionObserver` 的测试或旧浏览器环境无法自动加载 → 检测 API 是否存在；核心分页逻辑仍由 hook 管理并可独立测试。
- [权衡] 已加载的页面会保存在客户端内存中，用户持续滚动仍会逐步增加列表大小 → 单次请求和首屏内存被限制；虚拟列表不在本次范围内。
