## Context

评论创建把数据库提交和通知准备串联成一个成功结果；通知二次读取失败会在评论已落库后返回错误。媒体 Repository 同时访问数据库和 S3，并先删除数据库记录，导致对象删除失败后丢失可重试 key。用户明确选择同步、低复杂度方案，不接受 Outbox、Cron 或队列。

## Goals / Non-Goals

**Goals:**

- 评论提交后不因通知失败向客户端报告业务失败。
- 媒体外部删除失败时保留数据库记录和重试信息。
- 让 Application 显式协调副作用，Repository 保持单一基础设施职责。
- 保持现有 API 输入输出兼容。

**Non-Goals:**

- 不保证通知最终必达。
- 不引入持久任务、后台 worker、新表或第三方队列。
- 不实现跨数据库与对象存储的原子事务。

## Decisions

### 评论以数据库提交为成功边界

`createComment` 在创建成功后直接基于创建结果返回公开 DTO。通知函数在一个完整 `try/catch` 边界中执行，包含通知所需查询和邮件发送；任何失败只写脱敏结构化日志。选择可能丢失通知，是对当前体量下低复杂度的明确取舍。

### 媒体采用存储优先的同步删除

Application 先通过 Repository 获取待删除媒体的最小 `{ id, key }`，再调用 `MediaStorage.deleteObjects(keys)`，最后删除数据库记录。对象存储删除失败时数据库不变；对象删除成功但 DB 删除失败时，重试依赖 S3 批量删除不存在 key 的幂等语义。

### 分离数据库端口与存储端口

Media Repository 不再导入 S3。Router 只进行依赖装配并调用 Use Case，不承载顺序或错误处理。

## Risks / Trade-offs

- [通知可能永久丢失] → 保留结构化错误日志，接受这是无队列方案的显式限制。
- [对象已删但数据库删除失败] → 数据库仍保留 key，重试再次执行幂等对象删除后完成 DB 删除。
- [同一媒体被并发删除] → 查询与最终删除均按 id 集合工作，空集合和不存在对象视为幂等成功。
- [S3 实现改变幂等语义] → 在 Storage adapter 测试中固定删除不存在对象不导致业务失败的契约。

## Migration Plan

1. 先添加 Application 失败路径测试。
2. 调整评论成功边界和通知日志。
3. 拆分 Media Repository 与 Storage 端口并调整删除顺序。
4. 更新 Router 装配和现有测试。
5. 运行相关 E2E、完整质量门禁和构建。
