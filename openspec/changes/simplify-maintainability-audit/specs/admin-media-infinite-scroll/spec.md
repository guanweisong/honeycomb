## MODIFIED Requirements

### Requirement: 媒体列表必须使用有界分页

媒体管理页 MUST 以固定页大小请求媒体数据；缓存可复用时不强制将重挂载的列表退回第一页。

#### Scenario: 首次加载请求第一页

- **WHEN** 用户打开没有可复用账户查询缓存的媒体管理页
- **THEN** 系统使用 `page: 1` 和 `limit: 50` 请求媒体列表

#### Scenario: 后续加载请求下一页

- **WHEN** 当前页已加载且仍有未加载记录
- **THEN** 系统请求递增后的页码，并继续使用 `limit: 50`

### Requirement: 分页协调依据查询身份而非内容相等

媒体列表 MUST 由 TanStack Query 的单一 InfiniteData 缓存拥有 pages/pageParams，不另建组件累计页缓存。每页通过真实 pageParam 协调有效结果；MUST NOT 因相邻页 ID 相同而拒绝有效结果。展示结果按 ID 去重，完成或取消请求后允许后续有效加载。

#### Scenario: 相邻分页返回相同ID

- **WHEN** 并发插入导致合法下一页内容ID与上一页相同
- **THEN** 查询按真实页身份完成协调并允许继续加载，不永久显示加载更多

#### Scenario: 第一页刷新未改变数据

- **WHEN** 刷新成功但查询缓存复用原数据引用
- **THEN** 已有第一页仍可见，不因等待新的引用而成为空列表

## ADDED Requirements

### Requirement: 媒体分页采用原生刷新与缓存复用

媒体列表 MUST 使用原生无限查询刷新语义：需要刷新时从第一页起依次重读已加载的分页，而不是只刷新当前页；不新增后端批量请求 API。重挂载可复用当前账户与查询已加载的缓存，同账户同查询的多个消费者共享分页进度；不同账户查询 MUST 隔离。上传或删除后的显式 reset 仍按既有合同丢弃后续页并刷新第一页，保留已有首屏、失败重试、选择与通知语义。

#### Scenario: 已加载多页后需要刷新

- **WHEN** 已加载多页的有效媒体查询触发需要执行的刷新
- **THEN** 查询依次刷新已加载分页并按 ID 去重展示，不仅刷新最后一页

#### Scenario: 相同账户重新挂载或同时消费

- **WHEN** 相同账户和查询存在有效分页缓存，列表重新挂载或另一列表订阅
- **THEN** 消费者复用同一分页缓存和进度，不另建独立累计页状态

#### Scenario: 账户或会话切换

- **WHEN** 当前账户失效或切换
- **THEN** 不向新账户展示或合入旧账户分页响应，禁用状态不发起下一页请求

#### Scenario: 下一页失败后重试

- **WHEN** 下一页请求失败且用户显式重试
- **THEN** 保留已加载项目并重试失败页，不跳页、不重复并发加载

#### Scenario: 已解绑哨兵仍投递排队回调

- **WHEN** 列表已卸载或账户切换后，旧 IntersectionObserver 投递已经排队的回调
- **THEN** 旧观察器不请求下一页；当前账户的新观察器仍可正常加载
