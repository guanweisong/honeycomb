## 背景与目标

基线为已发布 master `b4a350e7`。只收敛同一技术机制，不改变业务契约；生产代码净增减与测试、文档分开报告。

## 决策

- 事务重试归数据库技术工具：只重试业务回调尚未进入的 SQLITE_BUSY，保留尝试次数、退避和调用方文案。拒绝通用 CRUD 或可重试任意业务回调的框架。
- 创建意图规范化归纯算法：固定测试锁定既有序列化和摘要字节；原始输入摘要不替换成清洗后正文摘要。
- 草稿恢复先在各编辑器内合并字段转换，问题状态、发布状态及版本基线由原调用点决定，不合并文章和页面编辑器。
- 错误码只抽相同的读取机制；若原消费者存在字符串转换或 ZodError 策略差异，保留差异，不借去重修正行为。
- 同步存储校验只在实际减少重复且不增加策略参数时抽取；保留各领域 schema、账户键及清除返回值差异。
- 页面重复 generation 清理只有在 layout cleanup 覆盖身份变化与卸载且回归通过后删除；不删除其他过期响应保护。

## 风险与验证

- 重放已进入事务的操作 → 验证业务回调和提交失败只执行一次。
- 摘要漂移 → 固定历史输入/摘要测试，不从被测函数计算期望。
- 草稿状态合并错误 → 覆盖冲突、旧基线、后来输入、账号切换、卸载与 StrictMode。
- 工具过度抽象 → 仅保留实际多消费者的小函数；收益不足的抽取不实施。

### 同步存储评估结论

本轮保留现有实现。单独抽取 `setItem/getItem` 不能覆盖领域 schema 解析及序列化异常，调用方仍需异常边界；若将解析函数注入公共工具，又增加策略参数。少量重复不足以抵消新模块和双层错误处理的成本，且文章与页面的清除返回值契约不同。
